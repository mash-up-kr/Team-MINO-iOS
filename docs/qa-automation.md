# QA 자동화 — 화면을 대신 눌러보는 도구

이 저장소에 화면 QA를 자동으로 돌리는 도구가 들어와 있다. 이 문서는 **처음 보는 사람이 읽는 안내**다.

## 먼저: 안 쓰면 아무 일도 안 일어난다

`.claude/` 아래 파일이 여러 개 늘었지만, **부르지 않으면 동작하지 않는다.** 빌드와 앱 코드에 영향이 없고 CI도
그대로다 — `layer-guard`는 `Packages/Domain/Package.swift`만 들여다보고, PR 자동 리뷰(`claude-code-review.yml`)는
허용 도구 목록에 `Skill`이 없어 이 스킬들을 부를 수 없다. **효력은 각자의 로컬 세션에서만 생긴다.**

평소처럼 작업하다가 필요할 때만 명령 한 줄로 부르면 된다.

## 뭐 하는 건가

화면을 다 만들고 나면 보통 시뮬레이터를 띄워 직접 눌러본다 — 버튼을 눌러 화면이 넘어가는지, 로딩이 끝나면
데이터가 보이는지. 그 반복 노동을 도구가 대신한다.

```
화면 작성 끝
  │
  ▼  ① 접근성 식별자 부여      버튼·목록·상태 표시에 자동화가 짚을 이름을 붙인다
  │
  ▼  ② 테스트·시나리오 작성    단위테스트 + "무엇을 어떤 순서로 누를지" 목록
  │
  ▼  ③ 빌드·설치              시뮬레이터에 올려 실행
  │
  ▼  ④ 시뮬레이터 구동         실제로 눌러보고 단계마다 스크린샷
  │
  ▼  ⑤ 판정                   스크린샷·테스트 결과로 통과/실패 판정 → PR에 붙일 리포트
```

각 단계는 서로 다른 담당이 맡는다. **만드는 쪽과 검사하는 쪽을 나눠, 자기가 만든 걸 자기가 통과시키지 못하게** 한
구조다. 중간에 조건이 안 맞으면 다음 단계로 넘어가지 않고 멈춰서 사람에게 보고한다.

## 어떻게 부르나

```
/mino-qa Packages/Feature/Sources/Feature/Map/Home/MapHomeView.swift
```

화면 파일 경로를 주면 ①~⑤가 순서대로 돈다. 단위테스트만 원하면 `--unit-only`, 화면 조작만 원하면 `--ui-only`.

기획서나 피그마부터 PR까지 통째로 진행하려면 `/mino`을 쓴다. 그쪽은 설계·구현 단계를 포함하며, 구현이 끝나는
지점에서 위 QA를 자동으로 불러 쓴다.

## 처음 한 번만 준비할 것

시뮬레이터를 외부에서 조작하는 `axe` 명령이 필요하다. 이건 저장소에 없고 각자 설치한다.

```
brew install cameroncooke/axe/axe
```

Command Line Tools가 오래됐다는 이유로 brew가 거부하면, [AXe 릴리스 페이지](https://github.com/cameroncooke/AXe/releases)의
prebuilt 아카이브를 받아 `PATH`에 넣어도 된다(빌드를 안 하므로 CLT 버전과 무관하다).

설치 확인:

```
axe --version
axe list-simulators
```

시뮬레이터는 미리 하나 부팅해 둔다. 안 띄워져 있으면 ④단계가 그 사실을 알리고 멈춘다.

## PASS가 무슨 뜻인가 — 이게 사람 확인을 대신하지는 않는다

**여기가 가장 중요하다.** PASS는 "**시나리오에 적힌 동선이 실제로 돌았다**"는 뜻이다. "화면이 시안대로다"거나
"버그가 없다"는 뜻이 아니다.

- 시나리오에 없는 동선은 검증되지 않는다. 리포트의 **「미검증 범위」** 항목을 꼭 본다.
- 판단이 애매하면 도구가 **「판정 보류」**로 따로 뺀다. 보류는 사람이 직접 확인해야 하는 항목이다.
- 디자인 대조(폰트·색·간격)는 사람 눈이 맡는다. 도구는 하지 않는다.

즉 **사람 확인의 대상을 줄여주는 것**이지, 없애주는 게 아니다.

## 지금 알려진 한계

| 한계 | 뜻 |
|---|---|
| 한글 입력 불가 | `axe`가 US 키보드 문자만 보낸다. 한글 입력 동선은 시드 데이터로 우회하거나 시나리오에서 뺀다 |
| 식별자가 없으면 못 찾는다 | ①을 안 거친 화면은 ④가 아무것도 짚을 수 없다 |
| 탭이 "처리됐는지"는 보장 안 됨 | 명령은 전송까지만 보장한다. 그래서 매 단계 스크린샷·접근성 트리로 따로 확인한다 |
| 지도 마커처럼 SDK 내부 요소 | GoogleMaps 마커는 개별 접근성 요소로 노출되지 않아 이름으로 짚을 수 없다. 장소 목록 행으로 우회한다 |
| 툴바 버튼은 이름이 두 번 잡힌다 | SwiftUI 툴바가 버튼을 감싸며 같은 이름을 컨테이너에도 물려준다. 시나리오가 `--element-type`으로 좁힌다 |

## 이 파일들은 어디서 왔나

| 경로 | 무엇 |
|---|---|
| `.claude/agents/` | ①~⑤ 각 단계 담당 정의 |
| `.claude/skills/mino-qa/` | ①~⑤를 순서대로 돌리는 절차 |
| `.claude/skills/mino/` | 기획서→PR 전체 흐름의 진입점 |
| `.claude/skills/{swiftui-expert,swift-concurrency,swift-testing-expert,axe}/` | 구현·리뷰가 근거로 읽는 외부 자료 |
| `.claude/docs/project-profile.md` | 이 프로젝트의 빌드·테스트 명령 등 사실 모음 |
| `scripts/verify_manifest.py` | ②와 ③ 사이 기계 검사 |
| `qa/manifests`·`qa/scenarios` | 화면별 식별자 목록과 조작 순서 |

`.claude/agents/`·`.claude/skills/mino-qa`·`scripts/`는 **[Mino-harness](https://github.com/hooni0918/Mino-harness)가
원본**이고, `make sync`로 이 저장소에 복사된 것이다. **이 디렉터리를 직접 고치면 다음 sync에 덮여 사라진다** —
고칠 일이 있으면 원본 저장소에서 고친다.

`swiftui-expert` 등 네 개는 외부 저장소에서 그대로 가져온 자료다. 출처·라이선스는 `.claude/skills/NOTICE`에 있고,
**내용을 수정하지 않는다**(갱신은 출처에서 다시 받는다).

## Claude 컨텍스트에 부담이 되나

파일 수가 많아 보여도 **전부 항상 읽히는 건 아니다.**

| 대상 | 언제 읽히나 |
|---|---|
| `.claude/docs/clean-architecture.md`, `mvi-coordinator-di.md` | **항상** — `CLAUDE.md`가 `@`로 가져온다 |
| `.claude/skills/*`, `.claude/agents/*` | 이름과 한 줄 설명만 목록에 올라가고, **본문은 부를 때** 읽힌다 |
| `.claude/docs/project-profile.md` | `@` 대상이 아니라, 빌드·테스트 명령이 필요한 단계에서만 읽힌다 |

즉 늘어난 건 대부분 "필요할 때 꺼내 쓰는 서랍"이고, 평소 대화에 늘 실려 다니는 양은 이름·설명 수준이다.

## 실제로 돌려본 결과

지도 화면(`MapHome`)으로 전 구간을 한 번 완주했다 — 홈에서 지도 열기 → 장소 목록 탭으로 카메라 이동 →
기본 위치 복귀 → 닫기로 홈 복귀. 판정 PASS.

만들어진 시나리오 파일을 **수정 없이 그대로** 다시 실행해도 4스텝이 통과한다(`axe batch --file`). 즉 산출물은
일회용이 아니라 회귀 검증에 재사용할 수 있다.

그 주행에서 도구 결함 4건을 찾아 원본 저장소에 반영했다 — 진입 화면 감사 누락, 툴바 식별자 이중 노출,
매니페스트 파일 분리 규칙, 게이트가 주석을 잘못 읽던 문제.
